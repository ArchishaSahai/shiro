# Execution Pipeline

The pipeline is the path one run follows from input to final output. Not every run uses every
stage, but every stage emits events when it is used.

## Stages

1. create runner
2. load session context
3. retrieve memory
4. call provider
5. execute requested tools
6. process handoffs
7. pause for approvals
8. validate structured output
9. persist memory
10. export trace

## Why order matters

Memory must be loaded before the provider needs context. Approvals must happen before risky
tools execute. Output validation must happen before another system consumes the result.

## Best practices

- Trace every stage that changes state.
- Keep tools small so pipeline failures are easy to locate.
- Do not skip approval for convenience in development.
- Validate output before writing to external systems.

## Common mistakes

- Reading memory after the provider call.
- Executing tools outside the runner.
- Treating output validation as a UI concern.
