# Contributing

Shiro is built around a small runtime surface. Contributions should preserve that shape:
engine services are long-lived, runners own individual executions, and providers remain
runtime adapters.

## Before changing code

- Identify which runtime boundary the change belongs to.
- Add or update trace events when behavior becomes observable.
- Keep provider-specific logic out of core execution.
- Keep user state out of agents.

## Good contributions

- clearer runtime contracts
- provider adapters
- trace exporters
- Studio integrations
- focused docs examples
- tests for runner behavior

## Review checklist

- Does the change preserve TypeScript inference?
- Does it emit enough trace data to debug?
- Does it avoid coupling core to one provider?
- Does it keep approvals explicit?
- Does it include a small example?

## Documentation

When adding a concept, explain what it is, why it exists, when to use it, and the common
mistakes. Avoid marketing language.
