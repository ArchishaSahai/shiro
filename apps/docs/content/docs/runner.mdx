# Runner

A `Runner` owns one execution. Application code usually does not instantiate it directly; the
engine creates it when you call `execute()` or start a stream.

## What it does

The runner keeps the run coherent. It decides when to call the provider, execute tools, switch
agents, pause for approval, load memory, validate output, and emit trace events.

## Why it exists

Agent execution is stateful. If provider calls, tool calls, and approvals are coordinated by
separate application code paths, the run becomes difficult to replay. The runner keeps those
transitions in one place.

## Example flow

```txt
run.started
provider.call
tool.execute
approval.required
approval.granted
provider.call
output.validated
run.completed
```

## Best practices

- Let the engine create runners.
- Subscribe to runner events for observability.
- Treat a rejected approval as a normal outcome.
- Keep tool side effects idempotent when possible.

## Common mistakes

- Reimplementing the execution loop outside Shiro.
- Mixing application logs with trace events.
- Continuing a run manually after an approval pause.
